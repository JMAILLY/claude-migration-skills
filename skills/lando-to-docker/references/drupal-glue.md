# Drupal glue: settings, sites.php, drush aliases, `.env`

What must change in the Drupal codebase so it talks to the Docker services
instead of Lando. The **linchpin** is `clear_env = no` in `www.conf` (see
`docker-images.md`) — it is what lets `settings.php` read `$_ENV[...]`.

## Which source holds the `.env` values

Compose passes `.env` to the container's real environment, so with
`clear_env = no` both `getenv()` and — given `E` in `variables_order`, the PHP
default — `$_ENV`/`$_SERVER` see it. But a Drupal project usually **also** parses
`.env` in PHP via `autoload.files`, and the two common loaders behave differently:

| `load.environment.php` | `$_ENV` / `$_SERVER` | `getenv()` |
|---|---|---|
| `vlucas/phpdotenv` — `Dotenv::createImmutable(__DIR__)->safeLoad()` | populated | **`FALSE`** |
| `symfony/dotenv` — `(new Dotenv())->usePutenv(TRUE)->bootEnv(…)` | populated | populated |

This matters as soon as anything outside `settings.php` reads an env var — a theme
hook, a module, a Drush command — because with `phpdotenv` a `getenv()` call
returns `FALSE` and the code silently takes the wrong branch. Prefer
`symfony/dotenv` (`composer require drupal/dotenv` pulls it in) so all three
sources agree:

```php
// load.environment.php
use Symfony\Component\Dotenv\Dotenv;

(new Dotenv())->usePutenv(TRUE)->bootEnv(DRUPAL_ROOT . '/../.env');
```

`DRUPAL_ROOT` is available here even though this file runs from Composer's
`autoload.files`: `drupal/core` declares `includes/bootstrap.inc` in its own
`autoload.files`, and dependency files load before the root package's.

Whichever loader is in place, **read one source consistently across the project**
(the snippets below use `$_ENV`) rather than writing
`$_ENV['X'] ?? getenv('X')` chains that hide which one is authoritative.

## `.env.example`

```dotenv
# Container name prefix AND Traefik hostname base → https://<name>.dev.localhost
COMPOSE_PROJECT_NAME=myproject

# Host UID/GID — entrypoint remaps www-data to these (run `id -u` / `id -g`)
USER_ID=1000
GROUP_ID=1000

# Xdebug: develop,debug | off (off for performance)
XDEBUG_MODE=off

APP_ENV=local

# Database — host is the compose service name (or a network alias)
MYSQL_HOSTNAME=db
MYSQL_PORT=3306
MYSQL_DATABASE=drupal
MYSQL_USER=drupal
MYSQL_PASSWORD=drupal
MYSQL_PREFIX=

# Redis (empty password = no auth, as redis:7-alpine runs unauthenticated)
REDIS_HOSTNAME=redis
REDIS_PORT=6379
REDIS_PASSWORD=

# Generated by `make init`
HASH_SALT=

TRUSTED_HOST_PATTERNS=\.dev\.localhost$

# Mail — Mailpit catches everything in dev
SMTP_TRANSPORT=mailpit
SMTP_HOSTNAME=mailpit
SMTP_PORT=1025
SMTP_USER=
SMTP_PASSWORD=
SMTP_EMAIL_FROM=noreply@example.com

# Frontend
THEME_FOLDER=frontend
VITE_SERVER_HOST=localhost
VITE_SERVER_PORT=3000
VITE_DEV_URL=https://myproject-vite.dev.localhost

# Optional integrations
CAPTCHA_SITE_KEY=
CAPTCHA_SECRET_KEY=
GTM_CODE=
```

`.env` is git-ignored; `.env.example` is committed and 1:1 with it.

## Single-site `settings.php` (DB + Redis + reverse proxy)

Read connection details from `$_ENV`. Host = the compose service name (`db`) or
a network alias. The **reverse_proxy block is required** because Traefik
terminates TLS and the container only sees plain HTTP:

```php
$databases['default']['default'] = [
  'database'  => $_ENV['MYSQL_DATABASE'] ?? 'drupal',
  'username'  => $_ENV['MYSQL_USER'] ?? 'drupal',
  'password'  => $_ENV['MYSQL_PASSWORD'] ?? 'drupal',
  'prefix'    => $_ENV['MYSQL_PREFIX'] ?? '',
  'host'      => $_ENV['MYSQL_HOSTNAME'] ?? 'db',
  'port'      => $_ENV['MYSQL_PORT'] ?? '3306',
  'driver'    => 'mysql',
  'namespace' => 'Drupal\\Core\\Database\\Driver\\mysql',
];

$settings['config_sync_directory'] = '../config/sync';
$settings['hash_salt'] = $_ENV['HASH_SALT'] ?? '';
$settings['trusted_host_patterns'] = !empty($_ENV['TRUSTED_HOST_PATTERNS'])
  ? explode(' ', $_ENV['TRUSTED_HOST_PATTERNS'])
  : [];

// Traefik terminates TLS — trust X-Forwarded-* so Drupal detects HTTPS
$settings['reverse_proxy'] = TRUE;
$settings['reverse_proxy_addresses'] = [$_SERVER['REMOTE_ADDR'] ?? '127.0.0.1'];

// Redis — guard empty password (PhpRedis throws "ERR AUTH without any password")
$settings['redis.connection']['host'] = $_ENV['REDIS_HOSTNAME'] ?? 'redis';
$settings['redis.connection']['port'] = $_ENV['REDIS_PORT'] ?? 6379;
$settings['redis.connection']['password'] = !empty($_ENV['REDIS_PASSWORD']) ? $_ENV['REDIS_PASSWORD'] : NULL;

// Dev cache: null the render/page bins so template edits show immediately.
// Fail closed — never default to 'local' (see "Gate on APP_ENV" below).
if (($_ENV['APP_ENV'] ?? NULL) === 'local') {
  $settings['cache']['bins']['render'] = 'cache.backend.null';
  $settings['cache']['bins']['page'] = 'cache.backend.null';
  $settings['cache']['bins']['dynamic_page_cache'] = 'cache.backend.null';
}
```

> `web/sites/*/settings.php` is often git-ignored (a local file). If so, the
> Docker glue lives there and you edit the developer's local file rather than a
> tracked one — which means every teammate re-derives it by hand. **Prefer a
> tracked `base.settings.php`** included from `settings.php` (the php entrypoint
> can append that `include` on container start, so a fresh clone needs no manual
> edit). Then the whole team gets identical local wiring, and later skills that
> need shared local overrides — `gulp-to-vite` puts the CSS/JS-aggregation and
> `page.max_age` kill-switches there — have somewhere to write.

### Gate on `APP_ENV`, fail closed

A tracked settings file ships to every checkout, so guard the **whole file** once
at the top rather than sprinkling per-block conditions:

```php
// SAFETY: this file only ever applies to local development. On prod/staging,
// settings.php is assembled by CI and never includes it — but the guard means
// that even if it were included, it could not overwrite real credentials.
if (($_ENV['APP_ENV'] ?? NULL) !== 'local') {
  return;
}
```

**Never write `$_ENV['APP_ENV'] ?? 'local'`.** That is fail-**open**: an
environment where the variable never arrived (missing `clear_env = no`, a CI job
that forgot to pass it) silently gets the dev behaviour. The strict comparison
already rejects absent, empty, `prod` and `preprod` — no fallback needed. Local
always sets `APP_ENV=local`, so an empty value never legitimately means "local".

## Drush

Drush runs **inside** the php container, so a single-site install needs no
Docker-specific alias — `drush` resolves the `default` site. If the project uses
per-site drush aliases (`drush/sites/*.site.yml`), update `root` and `uri`:

```yaml
# BEFORE (Lando)
myproject:
  root: /app/web
  uri: myproject.lndo.site
# AFTER (Docker)
myproject:
  root: /var/www/html/web
  uri: https://myproject.dev.localhost
```

## Multisite variant (the ginger-cebtp model)

One shared MariaDB serves N sites; each site has its own DB+user, reached via a
per-site **network alias** on the `db` service (see `compose-traefik.md`).

### `web/sites/sites.php` — hostname → site id

```php
// AFTER — hostnames match COMPOSE_PROJECT_NAME style, .dev.localhost
$sites['site_a.dev.localhost'] = 'site_a';
$sites['site_b.dev.localhost'] = 'site_b';
$sites['site_c.dev.localhost'] = 'site_c';
```

### `docker/mariadb/init/01-databases.sql` — one DB+user per site

Runs **only on first init of an empty data volume** (after editing it, run
`make destroy` to re-provision). Convention: **database = username = password =
`<site_id>`**.

```sql
CREATE DATABASE IF NOT EXISTS `site_a` CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
CREATE USER IF NOT EXISTS 'site_a'@'%' IDENTIFIED BY 'site_a';
GRANT ALL PRIVILEGES ON `site_a`.* TO 'site_a'@'%';
-- repeat per site …
FLUSH PRIVILEGES;
```

Mount it in the `db` service: `- ../../mariadb/init:/docker-entrypoint-initdb.d:ro`.

### Per-site DB config in `base.settings.php`

The DB host falls back to the site id, which resolves through the network alias:

```php
$site_id = $settings['current_multisite'];           // set by the site bootstrap
$env_site_prefix = strtoupper($site_id) . '_';         // e.g. SITE_A_

$databases['default']['default'] = [
  'database' => $_ENV[$env_site_prefix.'DB_DATABASE'] ?? $site_id,
  'username' => $_ENV[$env_site_prefix.'DB_USERNAME'] ?? $site_id,
  'password' => $_ENV[$env_site_prefix.'DB_PASSWORD'] ?? $site_id,
  'prefix'   => $_ENV[$env_site_prefix.'DB_PREFIX']   ?? '',
  'host'     => $_ENV[$env_site_prefix.'DB_HOST']     ?? $site_id,   // = network alias
  'port'     => $_ENV[$env_site_prefix.'DB_PORT']     ?? '3306',
  'driver'   => 'mysql',
  'namespace'=> 'Drupal\\Core\\Database\\Driver\\mysql',
];
```

`.env` then carries one block per site (`SITE_A_DB_HOST=site_a`, …), and the
Makefile drives drush per site with `--uri=$(SITE)` (see `makefile.md`).

## What NOT to carry over

- **Elasticsearch** — none of the reference projects kept it; they run
  `search_api_db`. Don't stand up an ES service unless the project genuinely uses
  a `search_api_elasticsearch` server backend (`config/sync/search_api.server.*.yml`).
- **`Dockerfile.x64` / `platform: linux/amd64`** — dead Lando-era workaround;
  `node:22-alpine` is multi-arch.
- **phpMyAdmin / MailHog** — replaced by Adminer / Mailpit.
